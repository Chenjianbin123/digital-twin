# 病区选择与切换设计规格

日期：2026-07-24

## 1. 背景

当前应用在启动动画期间直接加载一个由环境变量指定的病区，动画结束后立即进入护士站。为了让同一套数字孪生模型支持不同病区，需要在启动动画之后增加病区选择页，并允许用户在护士站工作期间切换病区。

当前阶段不区分护士、医生或管理人员角色。所有用户都可以查看并切换所有启用病区。代码需要保留病区访问策略边界，未来接入用户权限后，只改变可见病区列表和切换许可，不重写页面与数据加载流程。

## 2. 目标

- 启动动画结束后统一展示病区选择页。
- 通过真实 SWP 接口加载启用病区。
- 用户选择病区后，按 `areaId` 加载该病区门口机、病房、床位和患者数据。
- 在护士站主界面顶部持续显示当前病区，并通过右侧抽屉切换病区。
- 护士站、病房走廊、病房内 3D 和 2.5D 视图始终使用同一个当前病区上下文。
- 轮询、告警、状态历史和确认记录不能跨病区串联。
- 切换失败保留原病区；快速连续切换时旧请求不能覆盖新结果。
- 预留病区权限策略，但本期默认返回所有启用病区并允许切换。

## 3. 非目标

- 本期不实现登录、角色管理、单点登录或服务端权限校验。
- 本期不按角色隐藏病区或禁用切换。
- 不一次性预加载所有病区的门口机和患者数据。
- 不为选择页额外请求每个病区的床位数、在线设备数或告警数。
- 不改造现有门口机详情、床位模板和 3D 场景的数据模型。

## 4. 用户体验

### 4.1 启动与首次选择

1. 启动动画期间初始化设备运行环境、文件地址并请求启用病区列表。
2. 病区列表使用 `areaName` 和 `areaCode` 展示，支持名称或编号搜索。
3. 上次成功进入的病区存在且仍启用时默认高亮，并标记“上次进入”。
4. 用户必须点击“进入某某病区护士站”确认，不自动跳过选择页。
5. 进入按钮触发当前病区数据加载；加载期间保持选择页可见并锁定重复提交。
6. 加载成功后进入护士站，并将病区 ID 保存为上次选择。
7. 首次加载失败时留在选择页，展示可重试错误，不出现空护士站。

### 4.2 工作中切换

1. 主界面顶部左侧显示当前病区名称，点击后打开右侧抽屉。
2. 抽屉展示全部启用病区、搜索框和当前病区标识。
3. 选择目标病区后，通过明确的确认操作开始切换，避免单击列表即误切。
4. 切换期间保留旧病区场景，并显示目标病区加载状态；不提前清空主界面。
5. 新病区全部加载成功后原子替换当前病区，关闭抽屉并回到护士站视图。
6. 切换成功后清空旧房间、床位、局部告警定位和旧病区状态历史。
7. 切换失败时继续显示原病区，恢复原病区实时刷新，并在抽屉内提示失败。

### 4.3 权限预留

病区列表在进入组件前经过统一访问策略：

```ts
interface AreaAccessPolicy {
  filterAreas(areas: HospAreaRecord[]): HospAreaRecord[];
  canSwitchArea(currentAreaId: number, targetAreaId: number): boolean;
}
```

本期默认实现不筛选任何启用病区，并始终允许切换。未来权限接口只需替换策略实现。`localStorage` 仅记录上次病区，不能作为权限来源。

## 5. 接口契约

### 5.1 查询病区

请求：

```http
POST /swp/hosp/hospAreaInfo/queryHospAreaInfo
```

```json
{
  "areaCode": "",
  "areaName": "",
  "isEnable": "1",
  "pageNum": 1,
  "pageSize": 200,
  "sqlFilter": ""
}
```

响应读取 `code`、`message` 和 `data.records`。病区模型至少保留：

```ts
interface HospAreaRecord {
  id: number;
  areaName: string;
  areaCode: string;
  areaOutCode?: string;
  isEnable?: string;
}
```

客户端再次过滤 `isEnable !== '0'`、无效 ID 和空名称，并按接口顺序展示。病区总量超过 200 时再按 `pages` 继续请求，合并结果并按 ID 去重。

### 5.2 查询病区设备

请求：

```http
POST /swp/swpDeviceInfo/querySwpDeviceInfo
```

数字孪生场景只查询门口机：

```json
{
  "areaId": 192,
  "deptId": "",
  "deviceIp": "",
  "deviceName": "",
  "deviceTypeId": 4,
  "online": "",
  "pageNum": 1,
  "pageSize": 100,
  "sipNo": ""
}
```

开发和生产的 API 基础地址已经包含 `/swp`，因此代码中的相对路径分别使用：

- `hosp/hospAreaInfo/queryHospAreaInfo`
- `swpDeviceInfo/querySwpDeviceInfo`

设备查询分页字段统一为后端协议中的 `pageNum/pageSize`，不再使用当前的 `current/size`。门口机列表缓存键必须包含 `areaId`。

## 6. 组件与状态边界

新增职责：

- `hospital-area` API：请求、分页并规范化病区列表。
- 病区选择视图：搜索、选中和首次进入反馈。
- 病区切换器：顶部触发器、右侧抽屉和切换反馈。
- 病区访问策略：本期全量放行，未来接入权限。

Store 新增状态：

```ts
areaOptions: HospAreaRecord[];
selectedAreaId: number | null;
pendingAreaId: number | null;
isAreaListLoading: boolean;
isAreaSwitching: boolean;
areaListError: string | null;
areaSwitchError: string | null;
```

Store 提供三个明确动作：

- `loadAreaOptions()`：只加载病区列表。
- `enterArea(areaId)`：首次进入病区。
- `switchArea(areaId)`：从已加载病区切换到目标病区。

门口机数据加载函数必须显式接收 `areaId`，不能在切换流程中继续隐式读取固定的 `VITE_AREA_ID`。`VITE_AREA_ID` 仅作为上次选择不存在时的默认高亮候选。

## 7. 数据替换与并发控制

切换被视为一个事务：

1. 记录当前病区和当前请求序号。
2. 停止旧病区轮询和实时刷新。
3. 使用目标 `areaId` 加载门口机列表、门口机详情和床位模板。
4. 每个异步阶段完成后检查请求序号；不是最新请求则丢弃结果。
5. 完整结果成功后一次性替换 `TwinAreaEntity`、设备码和数据警告。
6. 重置到护士站，清除房间和床位选择，并切换当前病区 ID。
7. 清空旧病区状态历史，按病区维度读取告警确认记录。
8. 启动新病区轮询和实时服务。

如果任一步失败，不提交新病区状态，并重新启动旧病区服务。重复选择当前病区不触发网络请求。

定时刷新必须捕获刷新开始时的 `areaId`。刷新返回时若当前病区已经变化，则丢弃该结果。告警确认键增加病区 ID 前缀，避免相同房号和床号在不同病区发生冲突。

## 8. 异常处理

- 病区列表失败：启动动画结束后展示病区选择错误页和重试按钮。
- 病区为空：显示“暂无可用病区”，不进入护士站。
- 首次病区数据失败：保留选择页和已选病区，允许重试或选择其他病区。
- 工作中切换失败：保留原病区场景、选择和服务，在抽屉内显示错误。
- 部分门口机详情失败：沿用现有策略，至少有一个有效门口机时进入并展示警告；全部失败则整体失败。
- 请求超时：沿用统一 HTTP 超时错误，不把失败结果写入当前病区。
- 快速切换：只有最后一次请求允许提交状态。

## 9. 刷新与本地记忆

- 手动刷新只刷新当前 `selectedAreaId`，不重新选择病区。
- 60 秒定时刷新始终传当前病区 ID。
- 上次成功进入病区保存在单一稳定的本地键中。
- 病区列表刷新后，如果上次病区已停用或删除，则只默认高亮第一个启用病区。
- 页面刷新后仍先显示选择页，不自动进入上次病区。

## 10. 验收与验证

- 真实接口能返回并展示全部启用病区，搜索和默认高亮正确。
- 选择不同病区时，设备请求携带对应 `areaId` 和 `deviceTypeId: 4`。
- 首次进入后护士站、走廊、病房内 3D 和 2.5D 均只展示当前病区数据。
- 顶部当前病区名称与 Store 状态一致。
- 切换成功后返回护士站，旧病房和床位选择被清除。
- 切换失败后原病区保持可用，轮询恢复。
- 连续快速切换不会被较慢的旧请求覆盖。
- 手动刷新与定时刷新始终请求当前病区。
- 告警、状态历史和确认记录不会跨病区串联。
- `npm run build` 通过。
- 使用真实接口在桌面和移动视口进行视觉检查，确认选择页、抽屉、加载和错误状态无溢出或遮挡。

## 11. 实施范围

改动限制在病区 API/类型、病区选择与切换组件、Pinia Store、门口机查询参数、启动流程和对应样式。不会修改 3D 场景内部建模逻辑，也不会引入新的 UI 框架或权限依赖。
