## 1. 项目概述

### 1.1 一句话

**ward-digital-twin** = 智慧病房 **Web 端 3D 数字孪生原型**：把门口机、床头屏、输液、环境数据，变成护士站大屏上的**三种可交互场景**，共用一份 Pinia 状态。

### 1.2 三种场景

| 场景 | `sceneType` | 说明 |
|------|-------------|------|
| 护士站 | `nurse-station` | 工作台 3D + 排班看板 + 侧栏指标 |
| 病房 | `ward` | 走廊全景 + 各房门口机，可点进单房 |
| 病房内 | `ward-interior` | 单房 3D（`wardInteriorView: '3d'`）或 2.5D 平面（`'plan'`） |

三种场景**共用一份数据**（Pinia store），点同一张床，3D / 2.5D / 侧栏联动。

### 1.3 项目来源

智慧病房主项目（`medical-device-v2`）已有门口机数据、SWP 模板、输液推送，但缺少面向**护士站大屏**的空间可视化。

> **不是**从主项目 fork 的副本，而是**参照主项目 API 和数据结构独立搭建的可视化原型**，用于验证三场景方案，不影响主项目发版。

| 原因 | 说明 |
|------|------|
| 技术隔离 | Three.js 与业务页耦合成本高 |
| 快速试错 | Mock 先行，相机/布局/贴图反复调 |
| 职责清晰 | 主项目 = 设备业务；孪生 = 大屏可视化 |

### 1.4 核心能力

- 多病房（Mock 901～904 或 Remote `querySwpDeviceInfo` 拉取）
- 输液状态码驱动床位颜色/动画（对齐自研 `StatusCode`）
- 模拟床位呼叫（光环 + 病区高亮）
- 环境温湿度告警（场景变色 + 顶栏 + 历史）
- 相机预设（门口 / 巡视 / 俯视 / 自由）平滑过渡
- Mock 与 Remote 双数据源

### 1.5 设计原则

- **引擎与 Vue 解耦**：`WardScene` / `AreaScene` / `PlanRenderer` 为纯 TS class，Vue 只负责生命周期
- **API 模型 → 孪生模型**：接口数据先 `map` 成 `TwinAreaEntity`，3D 不直接绑 API 字段
- **模板即纹理**：SWP 模板 JSON → Canvas 2D → `THREE.CanvasTexture` 贴到 3D 屏幕

### 1.6 迭代阶段（怎么搭起来的）

| 阶段 | 做了什么 | 关键文件 |
|------|----------|----------|
| ① 定模型 | API 类型 → 孪生实体 | `types/ward.ts`、`types/twin.ts` |
| ② 单源状态 | Pinia 统一管理 | `stores/twin-store.ts` |
| ③ Mock 数据 | 没后端也能 demo | `mock/`、`api/door-device.ts` |
| ④ 单房 3D | 最先做的视图 | `core/ward-scene.ts` |
| ⑤ 2.5D 平面 | 文字信息密度高 | `core/plan-renderer.ts` |
| ⑥ 护士站 + 走廊 | 三场景架构 | `core/area-scene.ts` |
| ⑦ 模板贴图 | SWP → Canvas → 3D 屏 | `core/template/` |
| ⑧ 联调推送 | Mock 模拟 + Remote 环境 | `services/` |

## 2. 快速开始

### 2.1 依赖

| 包 | 用途 |
|----|------|
| Vue 3.5 + Composition API | UI |
| Pinia 2 | 全局状态 |
| Three.js 0.184 | WebGL 3D、OrbitControls、CSS2DRenderer |
| TypeScript 5.7 | 类型 |
| Vite 5 | 构建 |
| Sass | 样式 + 响应式断点 |

### 2.2 命令

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # vue-tsc + vite build
npm run preview
```

### 2.3 体验路径

1. 默认 **护士站** — 3D 工作台 + 侧栏指标
2. 底部切 **病房** — 走廊全景，点门口机进单房
3. **点一张床** — 右侧出现详情
4. 底部切 **2.5D** — 看文字信息卡
5. Mock 模式下开 **模拟推送** — 看床色变化和事件历史

### 2.4 入口

```
index.html → src/main.ts → App.vue
                ↓
         createPinia + global.scss
```

`App.vue` 在 `onMounted` 时：

1. `initFileUrlPrefix()` — 静态资源域名
2. `store.loadArea()` — 加载病区
3. `remote` → `startRemoteServices()`；`mock` → `startSimulation()`

## 5. 核心数据流

### 5.1 启动加载

```
loadArea()
  → fetchDoorDeviceList()        # mock 或 remote
  → mapDoorListToTwinArea()      # DoorDeviceInfo[] → TwinAreaEntity
  → enrichAreaBedTemplateIds()   # 每床 queryBedDeviceInfo → templateId
  → area 写入 store
  → AreaScene.updateArea + syncDoorTemplates
```

### 5.2 输液推送（mock）

```
status-channel tick (3.5s)
  → status-pusher → updateBedStatus(bedCode, statusBarInfo)
  → pushHistory (category: infusion)
  → WardScene.updateBedVisual / AreaScene.updateRoomVisual
```

### 5.3 用户选床

```
Raycaster / PlanRenderer click
  → emit bedClick
  → store.selectBed(bed)
  → WardInfoPanel 展示 selectedBed + selectedStatus
```

### 5.4 环境更新

```
env-simulator (mock 5s) / env-fetcher (remote 单房 60s / 总览 120s)
  → updateEnv(areaId, sickroomId, doorEnvData) + envSync 接收状态
  → analyzeEnvAlert → EnvAlertBanner + WardScene tint + roomSummaries
```

## 6. 类型与领域模型

### 6.1 两层模型

| 层 | 文件 | 说明 |
|----|------|------|
| API 层 | `types/ward.ts` | `DoorDeviceInfo`、`StatusBarInfo`、`DoorSickInfo` |
| 孪生层 | `types/twin.ts` | `TwinAreaEntity` → `TwinWardEntity` → `TwinBedEntity` |

**不要直接在 UI 里用 `DoorDeviceInfo`**，统一走 store 的 `Twin*` 类型。

### 6.2 关键映射

**文件：** `types/twin.ts`

- `mapDoorDeviceToTwinWard(doorData)` — 单门口机 → 单病房
- `mapDoorListToTwinArea(devices)` — 多门口机 → 病区
- `getWardRoomSize(bedCount)` — 1～6 人间房间尺寸
- `BED_LAYOUTS` — 床位在 3D 房间内的 x/z 坐标

### 6.3 输液状态码

**文件：** `types/ward.ts` → `StatusCode`

| 码 | 含义 |
|----|------|
| `300`/`301` | 输液中 |
| `302`/`305` | 输液完毕 |
| `304`/`307` | 离线 |
| `9` | 低电量 |
| `''` | 在院（无输液状态） |

可视化映射在 `core/bed-status.ts` 的 `STATUS_MAP`。

### 6.4 场景与相机

```typescript
type TwinSceneType = 'nurse-station' | 'ward' | 'ward-interior';
type WardInteriorView = '3d' | 'plan';
type CameraPresetId = 'free' | 'door' | 'nurse' | 'top';
```

### 7.3 主要 Actions

| 方法 | 何时调用 |
|------|----------|
| `loadArea()` | 启动、重试、reset |
| `setSceneType(type)` | 切换护士站 / 病房 / 病房内 |
| `enterRoom(i)` | 进入单房（`ward-interior` + cameraPreset=door） |
| `focusRoom(i)` | 走廊模式定位到某房门口 |
| `updateBedStatus()` | 输液推送 |
| `setBedCalling()` | 呼叫推送 |
| `updateEnv()` | 环境更新 |
| `startSimulation()` / `toggleSimulation()` | mock 模拟 |
| `startRemoteServices()` | remote 环境轮询 |

### 7.4 修改 store 时注意

- 改床位数据应改 `area.value.rooms[*].beds[*]` 上的字段，保持响应式
- 新事件类型需扩展 `HistoryCategory` 并在 `pushHistory` 调用处传入

## 8. API 与数据源

### 8.1 数据源切换

**文件：** `api/door-device.ts` → `getDataSource()`

由 `VITE_DATA_SOURCE` 控制：`mock` | `remote` | `database`（默认 mock）。

### 8.4 数据库模式（database）

`database` 模式不让浏览器直连 MySQL，而是通过 `server/db-adapter.mjs` 提供只读后端适配层：

```text
dnk_swp_db
  → server/db-adapter.mjs
  → /db-adapter/api/areas/:areaCode/twin
  → src/api/database-twin.ts
  → twin-store
  → 3D 场景 / 右侧面板
```

启动：

```bash
DB_PASSWORD='你的数据库密码' npm run dev:db-adapter
npm run dev
```

前端配置：

```bash
VITE_DATA_SOURCE=database
VITE_DB_ADAPTER_BASE=/db-adapter
VITE_DB_ADAPTER_TARGET=http://127.0.0.1:8788
VITE_DB_AREA_CODE=2001
```

后端适配器接口：

| 接口 | 说明 |
|---|---|
| `GET /health` | MySQL 连通性检查 |
| `GET /api/areas` | 可用病区列表 |
| `GET /api/areas/:areaCode/twin` | 返回前端统一 `TwinAreaEntity` 及设备、事件、医院信息 |
| `GET /api/templates/:id` | 从 `swp_template_info` 读取模板 |
| `GET /api/hospital` | 从 `hosp_hospital_info` 读取医院信息 |

核心表映射：

| 前端模型 | 数据表 |
|---|---|
| 病区 | `hosp_area_info` |
| 病房 | `hosp_sickroom_info` |
| 床位 | `hosp_bed_info` |
| 患者 | `out_sick_info` |
| 设备 | `swp_device_info` + `swp_device_type` |
| 呼叫 | `swp_call_info` |
| 报警 | `swp_alarm_info` |
| 最新体征 | `swp_physical_info` |
| 高危标签 | `out_sick_high_risk` |
| 模板 | `swp_template_info` |

安全约定：

- 数据库密码只放在服务端进程环境变量，不使用 `VITE_` 前缀。
- 患者姓名默认脱敏，由 `DB_MASK_PATIENT_NAME=true` 控制。
- 适配器目前只读，不提供写库接口。

### 8.2 Remote 数据加载流程

```
fetchDoorDeviceList()
  → querySwpDeviceInfo（一次拉全部门口机）
  → device/doorDevice/queryBaseDeviceInfo（按门口机 SN 拉完整病房/患者/床位）
  → normalizeDoorDevice() 归一化为 DoorDeviceInfo
  → mapDoorListToTwinArea() 转为 TwinAreaEntity
  → enrichAreaBedTemplateIds()（按需补床头 templateId）
```

**无需配置 SN。** 可选 `VITE_AREA_ID` / `VITE_DEPT_ID` 筛选病区。

### 8.3 主要接口（remote）

| Path | 用途 |
|------|------|
| `/swp/swpDeviceInfo/querySwpDeviceInfo` | 门口机 SN 发现 |
| `device/doorDevice/queryBaseDeviceInfo` | **门口机详情（病房、患者、床位主入口）** |
| `iot/.../queryRecentEnvRecordById` | 环境温湿度 |
| `device/bedDevice/queryBaseDeviceInfo` | 床头 templateId（进单房后按需） |
| `/swp/swpTemplateInfo/querySwpTemplateInfoById` | 模板 JSON |
| `device/commonDevice/querySysParamKeyValueByParamKeys` | 文件 CDN 前缀 |

### 8.4 归一化

**文件：** `api/normalize-door.ts`

- 过滤无效床位、按 `bedSort` 排序
- 默认 `deviceTypeCode = '201'`（门口机）
- `mapEnvRecords` 拼接单位（℃、%、dB）

## 9. 服务层（推送与环境）

### 9.1 Pub/Sub 结构

```
status-channel.ts  ──subscribe──► status-pusher.ts ──► store
call-channel.ts    ──subscribe──► call-pusher.ts   ──► store
```

**接真实 WebSocket 时只改 channel 层**，pusher 与 store 可保持不变。

### 9.2 Mock 场景

| 文件 | 周期 | 内容 |
|------|------|------|
| `status-channel.ts` | 3.5s | 901～904 各床输液状态轮换 |
| `call-channel.ts` | 6s | 90102、90308 等呼叫/解除 |
| `env-simulator.ts` | 5s | 温湿度随机波动 |

### 9.3 Remote 环境与刷新

**文件：** `services/env-fetcher.ts` — 启动立即拉一次；病房内部只查当前房间，每 60s 刷新，走廊/护士站查询全病区，每 120s 刷新。全局环境请求并发上限为 4，排队与在途同房请求去重。切病房/病区时立即查询并重新计时，同房间 3D/平面切换不重复查询。隐藏页面停止定时器并丢弃未发出的任务，返回前台立即补查；停止、切场景及快照替换后的旧响应不能覆盖当前数据。

**状态与汇总：** `core/environment-state.ts` 集中定义周期、并发和 5 分钟过期规则。接收时间不代表传感器采样时间；失败保留最后读数并立即标注，缺时间显示未知。病房侧栏通过时钟自动更新过期提示。护士站只将有效远程读数纳入当前均值和环境预警数，同时展示有效覆盖、待更新及异常待核实数量；过期异常继续留在任务与交班摘要中待核实。演示数据、数据库快照明确标注来源，并保留其统计展示。

**屏幕刷新：** 相同四项环境值不再替换 `doorEnvData`，但接收状态继续更新；走廊及普通门口屏的签名排除 `envSync`，仅同步时间或失败标志改变不会重绘纹理。实际环境/患者/医护数据、模板缓存代次变化和原有纹理 TTL 仍会触发刷新。普通门口屏签名按模型绑定保存，解绑或销毁后丢弃旧结果。

**文件：** `services/remote-area-fetcher.ts` — 默认每 5 分钟重新拉取病区快照，刷新病房、患者、床位与状态基础数据；刷新时保留当前场景位置，不自动跳回护士站。同病区快照替换时，仅按病房 ID 与设备编码保留匹配房间已确认的环境读数和原接收时间，不伪造新的更新时间。

**验收入口：** `scripts/env-fetcher-polling.test.mjs` 覆盖周期切换、并发和旧响应；`scripts/env-screen-refresh.test.mjs` 覆盖纹理去重、TTL、失败重试和解绑；`core/environment-state.test.ts` 与护士站模型测试覆盖过期、未知、静态来源和统计口径。浏览器合成数据页面为 `scripts/fixtures/environment-refresh.html`，对应检查脚本为 `scripts/environment-refresh.browser-check.cjs`，不访问医院接口。

## 11. 模板渲染子系统

数字孪生平台已接入 `@uneven/tpl-runtime@0.2.4`。所有接口模板统一将 `templateContent` 交给官方包解析；包支持的历史格式在内存中迁移为 TP4，再绑定数据生成 DOM，通过 `html-to-image@1.11.13` 转为 Canvas，贴到现有 Three.js 床头屏和门口屏。宿主不再按 `schemaVersion`、`isNew` 或 `analyzeType` 选择解析器。

### 11.1 责任边界与后台对应关系

| 层次 | 后台 `_swp-admin_v2` | 当前数字孪生平台 |
|---|---|---|
| 模板设计 | Studio 编辑 pages、regions、widgets、绝对 bounds、绑定及主题 | 不引入编辑器，消费已保存模板 |
| 模板正文 | `templateContent` 保存模板 JSON，包含存量格式及 TP4 | `queryTemplateById` 读取正文；原有 `templateJson` 兜底仍有效 |
| 编译产物 | `runtimeBundle` 含 `bundleVersion`、dataSources、checksum | 不直接交给 npm 包；它不是 TP4 正文，并且编译时不保留区域 editor.bounds |
| 协议解释 | `TemplateRuntimeRenderer.vue` 使用 npm runtime | `tp4-parser.ts` 调用官方 `parseTemplateAsTP4`；`runtime-renderer.ts` 调用 `createTemplateRuntime` |
| 业务数据 | 后台预览数据/设备端数据源 | 宿主提供当前房床、医护和环境数据；运行库不请求临床业务接口 |
| 显示 | DOM 预览 | 离屏 DOM → Canvas → `THREE.CanvasTexture` |

已通过 npm 官方仓库安装并锁定精确版本，许可证分别为 ISC、MIT。`html-to-image` 仅承担 DOM 截取，不重新实现模板组件。升级任一包时应重新跑模板验收。

### 11.2 当前实际解析链

```text
设备接口返回床头 bedDeviceInfoVo.templateId / 门口 doorDeviceInfo.templateId
  → queryTemplateById(id)
  → loadParsedTemplate(id) + 文件前缀就绪
  → parseTemplateInfo(info)
  → parseTemplateAsTP4(info.templateContent, context)
      → 包识别协议；支持的历史格式迁移为 TP4
      → 宿主尺寸/页面校验
      → buildBedRuntimeData / buildDoorRuntimeData
      → createTemplateRuntime（每次快照独立实例与文档副本）
      → 等待字体、布局、二维码 → 图片内嵌 → html-to-image.toCanvas
  → 床头/门口纹理出口 → THREE.CanvasTexture（sRGB）
  → 刷新 token 与模板缓存代次检查 → 过期结果 dispose / 有效纹理替换
```

- 接口不必额外提供 `schemaVersion`。正文原样交给包识别；所有正式加载入口取得 TP4 文档后使用同一个运行时，不增加页面开关。
- `context` 传入模板 ID、名称、`systemType`、`templateType`。平台类型影响旧格式的无单位字号：Linux 为 px，Android/Harmony 为 rem。接口应返回正确元信息；缺失时沿用包默认值（Linux/bed），不在宿主猜测。
- 已有本地床头样本包含不合法的双重转义，保留仅在 JSON 语法错误时的一次修复，再交给同一个包。有效 JSON 的协议/内容错误直接报错，不回退自写解析器。
- 历史迁移只作用于内存，不改写数据库模板。旧 Canvas 辅助代码仍保留给直接调用者，但 `loadParsedTemplate → parseTemplateInfo` 正式加载链不再选择旧分支。
- TP4 使用 `meta.frame.width/height`，保留 `editor.bounds`；不再执行旧节点的像素转百分比。
- 拒绝无效/超大画布、空首屏、无效区域与不支持的协议版本，沿用现有错误纹理和重试入口。
- 排除仅供编辑器使用的 `patientOverviewEditor` 页面，截取第一张正式页面。
- 缓存按 templateId，信息 TTL 为 5 分钟；解析签名包含正文和解析相关元数据，不缓存患者纹理为跨床共享结果。床头和走廊屏幕的纹理 TTL 从成功应用后计时，到期后由下一次现有数据或场景刷新重新加载，没有新增定时轮询。
- 点击“刷新数据”会清理模板信息与解析缓存；走廊重试也会清理模板及屏幕缓存。缓存代次进入屏幕签名，确保相同 ID、相同床位数据仍会重新加载；旧请求、旧纹理与旧错误不能覆盖刷新后的结果。

### 11.3 如何使用后台新模板

1. 确认模板详情接口的 `templateContent` 包含完整模板 JSON（包支持的历史格式或 TP4），同时返回正确的平台/设备元信息；不要只返回 `runtimeBundle`。
2. 将该模板 ID 配置到对应设备：床头 `bedDeviceInfoVo.templateId`；门口 `doorDeviceInfo.templateId`。
3. 数字孪生按现有设备接口取得 ID 后自动查询正文并使用新运行库，无需手填模板 ID。后台修改相同 ID 的模板后，点击“刷新数据”可立即重新加载；也可等待 5 分钟缓存到期后的下一次数据或场景刷新。
4. 在目标医院核对模板图片文件前缀、图片服务器 CORS、字段绑定、字体和横竖屏。这里的本地验证不替代真实医院接口验收。

最小 TP4 正文示例（后端字段保存为此对象的 JSON 字符串）：

```json
{
  "schemaVersion": 4,
  "meta": {
    "systemType": "linux", "templateType": "bed",
    "frame": { "width": 800, "height": 480, "unit": "px" },
    "rootFontSize": 32, "density": "fixed"
  },
  "theme": { "colors": { "canvas": "#102a43" } },
  "dataCatalog": [],
  "pages": [{
    "id": "main", "key": "main", "name": "主屏", "role": "standard",
    "layout": { "type": "grid", "cols": 12, "rowHeight": 10, "gap": 0, "padding": [0, 0, 0, 0] },
    "regions": [{
      "id": "patient",
      "grid": { "col": 0, "row": 0, "colSpan": 12, "rowSpan": 10 },
      "editor": { "bounds": { "x": 32, "y": 120, "w": 736, "h": 120 } },
      "widget": {
        "id": "patient-name", "kind": "primitive.text",
        "content": { "source": "dataSource", "path": "bedSickInfoVo,sickName" },
        "style": { "fontSize": 48, "color": "#ffffff" }
      }
    }]
  }]
}
```

绑定路径沿用包的逗号分段形式，如 `bedSickInfoVo,sickName`、`bedDeviceList,sickInfo,sickName`。门口多床组件的协议类型是 **`repeater.bedList`**，不要将旧编辑器组件名 `HBedList` 直接当作 `kind`。

### 11.4 宿主注入的数据

| 屏幕 | 数据源 | 来源/处理 |
|---|---|---|
| 床头 | `bedDeviceInfoVo` | 当前床位的原始设备字段与床号、设备号、在线状态 |
| 床头 | `bedSickInfoVo` | 当前患者对象；空床只保留床位身份，清空旧患者字段 |
| 床头 | `bedSickNursingLabelList` | 当前护理标签；空床清空 |
| 床头 | `statusBarInfo` | 现有输液状态与文案；空床清空 |
| 床头 | `__emptyBedPreview` | 明确当前是否空床，显示运行库内置空床卡 |
| 门口 | `doorDeviceInfo`、`bedNum` | 当前房间、设备与病区信息 |
| 门口 | `bedDeviceList` | 所有实体床，包含空床；每床独立作用域，沿用原姓名脱敏 |
| 门口 | `doorSickInfoList` | 与实体床逐一对应的患者数据 |
| 门口 | `doorMainDoctorAndNurseVo`、`doorDeptUserList` | 房间负责人、医护列表 |
| 门口 | `doorEnvData` | 当前房间环境参数，不新建轮询 |

### 11.5 纹理适配的约束

- **这是三维屏幕快照。** 文本、图片、二维码、护理标签、静态布局可进入纹理；点击跳转、原生设备指令不执行，视频/iframe 显式报错。没有接入护士站白板/看板页面渲染。
- 自动轮播在文档副本中关闭，保留 `initialSlide`；CSS 动画冻结。多页模板取第一张正式页面。时钟不会在纹理上自行逐秒运行，随原业务刷新流程更新。
- 图片使用现有 `FILE_FRONT_URL_HEAD` 前缀。截取前先内嵌可见图片和背景图；网络、解码或跨域失败会进入错误状态，避免静默缺图。外部字体不随截图下载，使用宿主字体。
- 包内置空床图的终端路径映射为本地 SVG，避免依赖终端部署目录；仅对 0.2.4 内置空床卡的 padding/字号作尺寸适配，不改模板作者的组件样式。
- 最多同时创建两个离屏运行时；**15 秒总期限包含排队、布局、资源和截取**。超时任务退出队列，释放名额，避免旧场景的大批慢任务逐个阻塞新画面。
- 每次成功/失败/超时均销毁 runtime、ResizeObserver、轮播计时器并移除 DOM。原场景的 refreshToken 和纹理 dispose 继续阻止过期结果覆盖新房床数据。
- 逻辑画布上限为单边 8192、总像素 16,777,216；截取 Canvas 单边最多 2048。床头目标宽 512，门口保留原横竖屏与 contain/fill 处理。

### 11.6 旧模板兼容范围

历史模板由包在加载时迁移到内存中的 TP4 文档，不写回数据库。迁移能力不等于已核对所有医院的布局、资源和业务组件。

存量 flat `data`、V3 `componentList` 和 TP4 都走 `parseTemplateAsTP4`；包负责坐标、组件和绑定转换。三份本地旧模板均有解析及浏览器回归，另覆盖 `isNew: false` 与 V3 多页输入。原 `parseTemplateContent` 工具仍保留，但不再属于接口模板的正式解析链。

视觉复核发现本地门口竖屏旧样本的长房间名、日期有溢出，需在后台按运行库字号与布局语义校准；不在宿主另写一套迁移规则掩盖差异。此轮浏览器检查证明解析、数据绑定与纹理生成可用，不代表存量模板与原 Canvas 完全像素一致。

| 旧节点 | 对应业务数据 |
|---|---|
| `patientName`、`bedNum`、`hosNum`、`hosDate` | 床头患者、床号、住院号、入院时间 |

- 优化 SWP 活动事件查询和轮询，只有接口返回 `eventStatus=0` 的记录才作为当前活动事件处理。
- 移除基于时间的“疑似历史未结束”判断，避免前端自行隐藏真实的活动呼叫；SWP 呼叫在平台内保持“呼叫中”，页面只提供定位。

- 移除数字孪生页面对 `/device/commonDevice/saveCallEvent` 的调用，避免没有语音通道的浏览器页面伪造已接听状态；后端 `eventStatus=0` 仍是活动呼叫的唯一依据。
- 呼叫卡明确提示“请在护士站管理机或话机上接听”；真正接听仍由管理机或话机完成。
- 移除活动 SWP 呼叫的“本地隐藏”和恢复入口，避免后端仍在呼叫时被浏览器本地状态遮蔽；旧的本地隐藏记录也不再影响活动呼叫。
- 增加可手动开启的呼叫提示音和浏览器系统通知，同一呼叫批次只提醒一次，避免每轮查询重复响铃。
- 页面处于后台时，活动呼叫查询由前台每 60 秒调整为后台每 240 秒，回到前台后立即补刷，兼顾提醒时效和接口压力。
- 修复活动呼叫查询复用历史统计分页导致的连续请求：`querySwpCallInfo` 和活动报警每轮只读取一页，近24小时响应统计继续分页且最多读取 20 页。
- 优化护士站任务操作区：默认展示 4 条优先任务，超出后支持展开全部和收起；SWP 呼叫只保留定位，环境、设备、输液等任务继续支持标记“处理中”和完成处理。
- 呼叫提醒开关通过浏览器 `storage` 事件同步到同源的其他标签页；旧的 SWP “已查看/本地隐藏”记录不再影响活动呼叫展示。
- 增加呼叫源编码的保守定位兼容：标准定位字段为空时，仅在 `callFrom` 与现有房间、床位或设备编码完全一致时定位，不解析病房床位描述文本。
- 优化护士站任务排序：先按告警级别，再按发生时间从早到晚排列，让等待时间更长的同级呼叫优先展示。
- 增加任务等待时长展示，护士站任务卡会按当前时间显示已等待的分钟、小时或天数，并每 30 秒更新一次。
- 收紧活动呼叫生命周期：只要 SWP 接口仍返回活动事件，呼叫卡就持续显示；只有后端不再返回该活动事件时才从页面消失。
- 优化护士站呼叫列表视觉：活动呼叫增加信号脉冲、低频扫描光、实时状态指示和定位按钮光效，使任务卡与数字孪生 3D 场景风格统一；系统开启“减少动态效果”时会自动停用动画。
- 进一步精简呼叫卡：只保留护士能直接使用的级别、患者呼叫内容、接听提示、发生时间和当前状态；隐藏接收终端、接口返回、定位诊断、位置来源等技术字段，避免信息堆叠。
- 按“来源 ID + 发生时间”区分同一设备的不同呼叫批次；同一批次仍去重，不同发生时间会生成独立任务。
- 优化护士站任务优先级：同级任务中新的待处理呼叫优先于已进入“处理中”的旧呼叫；超过 5 分钟进入关注色，超过 10 分钟进入紧急色。
- 统一护士站呼叫 KPI 与告警任务列表的数据口径，避免 KPI 数量和实际展示列表不一致。
- 顶部增加数据源和健康状态提示，区分实时 SWP、数据库、模拟数据，以及同步中、部分同步、同步失败和数据过期状态。
- 优化告警到 3D 场景的联动：从任务卡进入床位后自动聚焦并高亮 8 秒，手动选床、离开场景或处理完成后自动清除高亮；无定位事件只停留在护士站。
- 优化 SWP 事件轮询：页面隐藏时暂停事件和响应指标请求，页面恢复可见时只补刷一次，并继续保留请求防重入和病区切换保护。
- 优化 SWP 事件异常轮询：接口连续失败时采用 30 秒、60 秒的短暂退避，避免服务异常期间持续高频请求；接口恢复后自动回到正常轮询频率。
- 优化护士站呼叫数据状态提示：正常时显示“呼叫数据已同步”；部分异常时提醒数据可能延迟并关注管理机或话机；完全异常时保留最近一次呼叫数据并明确标注，不向护士直接展示接口报错。
- 完善设备异常闭环：区分设备离线、异常离线和低电量，任务卡分别提示检查电源网络、检查设备连接或充电更换电池；设备恢复正常后告警自动消失。
- 统一设备异常口径：护士站汇总和病区房间状态分别统计离线、低电量，避免把低电量设备误显示为普通离线。
- 完善病房环境异常闭环：按温度、湿度、空气质量和噪音生成护士可执行的复核提示，多项异常统一汇总；环境恢复正常后任务自动消失。
- 统一环境读数展示：温度、湿度和噪音分别规范为 `℃`、`%`、`dB`，空气质量为“差”时按严重异常处理，避免漏报。
- 完善输液巡视闭环：`300/301` 统一显示“输液中”并生成“输液巡视”任务，提示护士按计划确认滴速和通路；`302/305` 显示“输液已完成”但不自动生成待处理任务，避免把已结束状态误当成新告警。
- 区分日常巡视和紧急响应：护士站新增“输液巡视”床位数，响应压力统计不再把普通输液巡视计入紧急告警数量，避免护士误判当前工作压力。
- 补充病区巡视闭环：重点病房列表同时显示待处理任务或待巡视床位数，点击病房即可进入对应场景，状态以最新真实数据自动刷新。
- 增加护士交班摘要：自动汇总本班未结束呼叫、设备异常、环境异常病房、输液待巡视和实时数据同步状态；只使用当前真实数据，不虚构处理人和处理时间。
- 收紧告警处理闭环：设备、环境和输液活动任务只允许标记“处理中”，不能由浏览器手动完成或隐藏；真实来源恢复后任务自动结束，并清理本次处理状态，下一次新异常重新进入待处理。
- 增加数据健康闭环：护士站分别展示床位患者、设备、环境、输液、呼叫报警的数据状态；病区四类数据沿用同一次病区快照口径，不虚构独立刷新时间，任何数据延迟或中断时都禁止页面据此判断“病区无异常”。
- 增加护士站告警工作队列：默认显示“未处理”，可切换“处理中/全部”，每项显示数量和队列摘要；筛选只改变展示，不修改真实 SWP 事件状态。

## 19. 上线候选版验收与回滚

### 19.1 一键验收

在项目根目录运行，使用与 lock 文件一致的 npm。需要 Node.js 22.18 或更高版本，以及已安装的项目依赖。

```powershell
npm ci
npm run verify
```

顺序：发布前检查 → 单元/边界测试 → 类型检查 → 生产构建 → 构建资源核对 → 浏览器合成验收。前置步骤失败会停止后续步骤，报告保留“未执行”，不会把跳过当作通过。该命令会重新生成 `dist`，但不修改业务源码、不提交、不推送、不部署。

浏览器运行器复用 Playwright CLI，不自动联网安装或升级依赖。优先使用项目内已安装的 `@playwright/cli`；否则显式指定现有 CLI 的 JavaScript 入口文件（不是 `.cmd` 启动器）：

```powershell
# 将下面的占位路径替换为本机实际已安装的位置；不要填写任何业务凭据。
$env:VERIFY_PLAYWRIGHT_CLI = 'D:/tools/playwright-cli/playwright-cli.js'
npm run verify
```

CLI 和它对应的浏览器必须事先可启动；该变量只影响验收，不参与前端打包。缺少 CLI、浏览器无法启动或检查没有明确返回 `passed: true`，均不能得到完整验收通过。

需要局部排查时：

```powershell
npm run verify -- --preflight-only
npm run verify -- --no-browser
```

两者都会明确记录缺少的检查；局部检查全部成功时仍返回退出码 **2（未完成完整验收）**。完整检查通过返回 **0**，检查失败返回 **1**。退出码 0 也只表示自动检查通过，不是正式发布授权。

### 19.2 报告与覆盖范围

每次生成独立目录 `output/playwright/verify-<时间>-<标识>/`，避免覆盖上次证据：

- `report.md`：各步骤通过/失败/未执行、耗时、截图链接、待人工确认项。
- `report.json`：同一结果的机器可读版本、Git HEAD/工作区文件清单、lock 摘要、静态资源检查、构建入口摘要。
- PNG：本次浏览器运行生成的截图；不引用旧截图冒充本次验证。
- 浏览器临时脚本与 CLI 产物仅在本次目录内。整个 `output/` 已忽略，不加入发布包。

报告不读取或复制私有 `.env*`、令牌、账号或数据库密码；生产配置检查明确标为“人工确认”，不虚构已通过。工作区清单仅记录文件名和 Git 状态，不是允许提交全部文件的清单。包含未提交内容时，HEAD 不能唯一代表本次构建，需发布负责人确认并形成可追踪版本后重新验收。

自动资源检查扫描 `src` 中静态 `/models/`、`/videos/`、`/draco/` 引用，包含保留的旧配置和预览入口，核对 `public` 与构建后的 `dist` 文件存在且非空；出现动态路径需显式核对。它不验证所有 GLB 内部节点、服务端模板图片、模型摆放及临床数据准确性，不能替代现场验收。

浏览器使用独立随机本地端口、独立会话与合成账号/记录；不读取私有环境文件，不配置后端代理，仅允许本地静态资源请求。开始时会主动发起一次预期被拦截的合成请求以验证隔离；其余未被测试模拟的接口请求会被阻止并导致验收失败。不会占用或停止现有 5173 开发服务。覆盖：

1. 护士站、走廊、病房的深浅色/窄屏和业务提示。
2. 登录 502、断网、错误响应、重试与角色确认。
3. 待处理分页、失败重试、病区切换的迟到结果隔离。
4. 房床筛选、重新获取、巡视核对清单导出。
5. 合成呼叫/输液由未处理变已处理后退出队列。

### 19.3 发布范围与配置检查

发布负责人逐项确认，不将报告中的所有未提交文件直接打包：

- [ ] 本次批准的代码、`package.json`、`package-lock.json`、运行时模型/视频均已纳入可追踪版本；实验文件和其他人的改动另行确认。
- [ ] 使用最终批准版本重新运行完整验收，保留本次报告与最终 `dist`；报告之后发生代码/资源/配置变化应重新构建验证。
- [ ] 仅部署最终 `dist` 的完整静态产物，不部署源码、`scripts/fixtures`、私有环境文件、诊断导出、患者资料或测试报告。检查并处理不希望公开的预览入口与 `public` 资源，不能擅自删文件。
- [ ] 明确使用 `remote` 还是 `database`，不能将 mock 数据作为生产数据。构建期 `VITE_*` 是浏览器可见配置，不能放数据库密码、长期令牌、私钥。
- [ ] 登录凭据由用户输入；不得固化 `VITE_API_TOKEN`。确认真实权限、病区隔离与会话失效。
- [ ] 确认 HTTPS、接口访问、文件资源访问与 CORS；不得为部署临时关闭鉴权或浏览器安全限制。

当前部署约定为 **同一份前端包可用于不同医院，业务接口固定 `9700/swp`、文件服务固定同 IP 的 `9704`**。`src/core/deployment-endpoints.ts` 是浏览器和开发代理共同的地址解析入口。本地开发使用 `.env.development.local` 的 `VITE_DEVICE_HOST`，为空时兼容旧的 `VITE_API_BASE_URL`；开发 remote 模式缺少有效地址会阻止启动。正式 remote 产物通过 `src/core/runtime-config.ts` 读取同目录的 `config.json`，不使用构建时的后端地址，不回退到网页主机或固定医院 IP。地址不得带账号密码、查询参数、片段或 `/swp` 之外的路径；已有端口会统一规范为 9700/9704。

协议以配置为准，未写协议时沿用 HTTP；不会为了通过检查把 HTTP 自动改成 HTTPS，也不会关闭证书校验。开发/预览代理不等于正式部署配置：生产包直接访问规范后的接口地址，HTTPS 页面必须有实际支持 HTTPS 的 API/文件服务。实际主机、TLS、跨域策略及端口开放仍需部署人员确认。

文件参数 `FILE_FRONT_URL_HEAD` 只有与配置的文件服务同主机、同协议、同 9704 端口时才会采纳，并保留其合法路径前缀；旧 IP、错误端口或非法值会回退到当前配置的 9704 根地址。应同步修正后台参数，尤其是存在自定义路径前缀时。后端直接返回的绝对图片 URL 不在此规则内，不擅自重写外部链接；若仍带旧 IP，需在资源数据侧核对。

现场发布：执行 `npm run build`，将完整 `dist` 部署到静态服务器，再编辑其中的 `config.json`：

```json
{
  "deviceHost": "http://该医院后端IP"
}
```

`public/config.json` 会随构建原样复制，默认地址为空，必须填写现场地址。生产 remote 启动会以 `cache: no-store` 读取配置（8 秒超时），校验成功后才导入 App、初始化登录和业务模块；文件缺失、JSON 无效、地址无效或网络失败会显示“平台启动失败”和重新加载按钮。同一站点修改后端地址后，旧医院的登录会话会被清除，需重新登录。正式 mock/database 模式不要求 SWP 运行时配置。

**生产切换 IP 只需修改已部署的 `config.json` 并刷新页面，不需要重新打包。** 服务器应为该文件设置 `Cache-Control: no-store`；文件不存在时必须返回 404，不能回退成 SPA 首页。Nginx 部署在根路径时，可在现有 server 内增加以下规则（子路径部署需调整 location）：

```nginx
location = /config.json {
    add_header Cache-Control "no-store" always;
    try_files $uri =404;
}
```

`config.json` 是公开文件，只放后端地址，不放令牌、账号或密码。正式 remote 的本地病区选择、关注记录和呼叫提醒回执按规范后的医院 API 地址分别保存，不读取原先不带医院标识的历史记录，避免跨医院误用；原记录不删除。其他 `VITE_*`（数据源、数据库适配器等）仍为构建期配置；修改它们需要重新构建。开发地址修改后重启服务。Vite 的代理配置不会随静态产物发布；跨域和 HTTPS 仍需按现场环境配置。

`database` 模式还需要独立部署适配器及其服务端环境配置；`VITE_DB_ADAPTER_BASE` 对应的同源路由需由正式服务器转发，数据库凭据只留在服务端。验收脚本不会连接或改动数据库。

### 19.4 部署步骤与现场验收

1. 确认发布负责人、目标服务器目录、测试病区、维护窗口、上一版产物位置和回滚执行人。
2. 从批准版本按 lock 安装依赖，使用正确数据源构建，将现场 IP 填入产物 `config.json` 后完成验收；将完整产物上传到**新的版本目录**，不直接覆盖正在服务的目录。升级时保留并核对现场地址，避免被新包的空配置覆盖。
3. 保留上一版完整静态文件、配套服务器配置及校验信息。新版本的入口 HTML 与其引用的哈希资源必须保持同一版本；切换期间保留旧资源供旧页面使用。
4. 先在测试地址验证登录、权限、三场景模型/视频/解码器、深浅色、页面刷新及实际护士站分辨率；确认缓存策略不会让新 HTML 引用缺失文件。
5. 由现场人员使用测试设备验证呼叫和输液 `eventStatus: 0 → 1` 后数量、队列和位置同步更新；巡视新记录对应正确病房/床位。确认“已关注”不会冒充“已处理”。不得在生产病区随意制造报警。
6. 验证断网、502、会话失效、快速切换病区、多窗口提醒及约定时长的持续运行。保留最后记录时必须提示待核对，不能显示为正常或零待办。
7. 现场负责人确认后再切换正式入口；观察错误、资源加载、提醒及数据新鲜度。记录版本、时间、验收人与回滚入口。

### 19.5 回滚与中止条件

出现登录大面积失败、跨病区/串床、真实事件遗漏、处理状态错误、关键资源失败、护士无法辨认关键提示时，应停止扩大使用并启动回滚评估。

回滚由获授权人员将静态入口切回**上一版完整产物及匹配配置**，不要混搭新旧 HTML/资源，也不要执行 Git 硬重置来代替部署回滚。恢复后重新验证登录、权限、资源和一条真实测试事件闭环。保留失败版本与脱敏诊断供排查，不直接删除现场证据。

本轮不包含数据库迁移。若后续版本涉及接口或数据库不兼容变更，前端回滚未必有效，必须另行制定并批准兼容与恢复方案。

### 19.6 实际生产包检查

在完整自动验收之外，针对已经生成的 `dist` 执行：

```powershell
$env:VITE_DATA_SOURCE = 'remote'
# 单个空格经应用 trim 后为空，避免 Windows PowerShell 将空字符串当成删除环境变量。
$env:VITE_API_TOKEN = ' '
$env:VERIFY_PLAYWRIGHT_CLI = 'D:/tools/playwright-cli/playwright-cli.js'
npm run build
# 构建完成后编辑 dist/config.json，填写现场 deviceHost。
# 再次构建会复制 public/config.json，因此需要重新核对产物配置。
npm run verify:deployment
```

该检查从被验收产物的 `config.json` 读取目标 IP，并核对生产登录请求；切换 IP 无需重新构建。它不读取私有环境文件来猜测目标，不启动真实后端代理。独立本地端口提供实际构建资源；模型、视频和解码文件通过 HTTP Range 核对，浏览器检查配置缺失、错误 JSON、非法地址、刷新切换医院、旧会话清除，以及实际登录页和 502/断网/重试。所有登录请求在独立测试会话中被模拟，未知请求被阻断；不向医院发送合成账号，不覆盖人工联调的浏览器会话。

结果存入 `output/playwright/verify-deployment-*/`，保留入口 SHA-256、资源状态和无真实患者数据的截图。缺少 CLI 或检查未执行不能判为通过。此结果不等于真实登录、模型内部渲染、设备报警处理或上线授权。

2026-10-09 运行时配置改造验证：定向回归 33/33 通过，类型检查和生产构建通过；实际生产包的配置异常、刷新切换医院、会话清除及登录重试检查通过。同一产物只修改 `config.json` 到第二个合成 IP 后复验通过，未重新构建。最终全量回归 773/775，未通过项为护士站控制面板 `v-show="panelsVisible"` 和旧“大屏模式”文案断言；本轮未修改这些界面行为。所有后台响应为隔离合成数据，真实医院接口仍待现场联调。

多个任务同时构建时，不要共同使用 `dist` 作为联调产物。在上述环境配置后，为本次验收生成独立目录：

```powershell
$releaseOutput = 'output/release/ward-check-' + [Guid]::NewGuid().ToString('N')
npm run build -- --outDir $releaseOutput
if ($LASTEXITCODE -eq 0) {
  # 编辑本次产物目录下的 config.json，填写现场后端地址。
  # 未配置有效地址时，验收会明确失败。
  $env:VERIFY_DEPLOYMENT_DIST = $releaseOutput
  npm run verify:deployment
}
```

`VERIFY_DEPLOYMENT_DIST` 未设置时仍检查 `dist`；设置后资源核对、预览和入口指纹均使用同一目录，不回退到共享 `dist`。验收前后入口文件不一致会判定失败。联调时应预览报告记录的产物目录，避免其他任务重新构建造成服务地址或资源版本变化。

### 19.7 测试病区真实闭环

使用现场授权账号自行登录并选择明确指定的测试病区。测试人员核对：呼叫/输液新增后进入队列，后台处理为 `1` 后队列及计数同步减少；巡视新记录的病房、床位与现场一致；断网保留记录但提示待核对，恢复后刷新；会话过期要求重新登录，快速切换病区不混入旧结果。记录测试时间、结果和脱敏事件标识，不记录密码、令牌或患者明文资料。

没有真实账号登录、没有设备触发或没有观察到 `0 → 1`，对应项应记录“待现场验证”，不能用合成数据测试替代。端口有 HTTP 响应只能证明可达，根路径 404 不能证明具体资源损坏或正常。自动化不得擅自在生产病区制造报警或修改事件状态。
