## 1. 项目概述

### 1.1 一句话

**ward-digital-twin** = 智慧病房 **Web 端 3D 数字孪生原型**：把门口机、床头屏、输液、环境数据，变成护士站大屏上的**三种可交互场景**，共用一份 Pinia 状态。

### 1.2 三种场景

| 场景 | `sceneType` | 说明 |
|------|-------------|------|
| 护士站 | `nurse-station` | 工作台 3D + 排班看板 + 侧栏指标 |
| 病房 | `ward` | 走廊全景 + 各房门口机，可点进单房 |
| 病房内 | `ward-interior` | 单房 3D（`wardInteriorView: '3d'`）或 2.5D 平面（`'plan'`） |

三种场景**共用一份数据**（Pinia store），点同一张床，3D / 2.5D / 侧栏联动。

### 1.3 项目来源

智慧病房主项目（`medical-device-v2`）已有门口机数据、SWP 模板、输液推送，但缺少面向**护士站大屏**的空间可视化。

> **不是**从主项目 fork 的副本，而是**参照主项目 API 和数据结构独立搭建的可视化原型**，用于验证三场景方案，不影响主项目发版。

| 原因 | 说明 |
|------|------|
| 技术隔离 | Three.js 与业务页耦合成本高 |
| 快速试错 | Mock 先行，相机/布局/贴图反复调 |
| 职责清晰 | 主项目 = 设备业务；孪生 = 大屏可视化 |

### 1.4 核心能力

- 多病房（Mock 901～904 或 Remote `querySwpDeviceInfo` 拉取）
- 输液状态码驱动床位颜色/动画（对齐自研 `StatusCode`）
- 模拟床位呼叫（光环 + 病区高亮）
- 环境温湿度告警（场景变色 + 顶栏 + 历史）
- 相机预设（门口 / 巡视 / 俯视 / 自由）平滑过渡
- Mock 与 Remote 双数据源

### 1.5 设计原则

- **引擎与 Vue 解耦**：`WardScene` / `AreaScene` / `PlanRenderer` 为纯 TS class，Vue 只负责生命周期
- **API 模型 → 孪生模型**：接口数据先 `map` 成 `TwinAreaEntity`，3D 不直接绑 API 字段
- **模板即纹理**：SWP 模板 JSON → Canvas 2D → `THREE.CanvasTexture` 贴到 3D 屏幕

### 1.6 迭代阶段（怎么搭起来的）

| 阶段 | 做了什么 | 关键文件 |
|------|----------|----------|
| ① 定模型 | API 类型 → 孪生实体 | `types/ward.ts`、`types/twin.ts` |
| ② 单源状态 | Pinia 统一管理 | `stores/twin-store.ts` |
| ③ Mock 数据 | 没后端也能 demo | `mock/`、`api/door-device.ts` |
| ④ 单房 3D | 最先做的视图 | `core/ward-scene.ts` |
| ⑤ 2.5D 平面 | 文字信息密度高 | `core/plan-renderer.ts` |
| ⑥ 护士站 + 走廊 | 三场景架构 | `core/area-scene.ts` |
| ⑦ 模板贴图 | SWP → Canvas → 3D 屏 | `core/template/` |
| ⑧ 联调推送 | Mock 模拟 + Remote 环境 | `services/` |

## 2. 快速开始

### 2.1 依赖

| 包 | 用途 |
|----|------|
| Vue 3.5 + Composition API | UI |
| Pinia 2 | 全局状态 |
| Three.js 0.184 | WebGL 3D、OrbitControls、CSS2DRenderer |
| TypeScript 5.7 | 类型 |
| Vite 5 | 构建 |
| Sass | 样式 + 响应式断点 |

### 2.2 命令

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # vue-tsc + vite build
npm run preview
```

### 2.3 体验路径

1. 默认 **护士站** — 3D 工作台 + 侧栏指标
2. 底部切 **病房** — 走廊全景，点门口机进单房
3. **点一张床** — 右侧出现详情
4. 底部切 **2.5D** — 看文字信息卡
5. Mock 模式下开 **模拟推送** — 看床色变化和事件历史

### 2.4 入口

```
index.html → src/main.ts → App.vue
                ↓
         createPinia + global.scss
```

`App.vue` 在 `onMounted` 时：

1. `initFileUrlPrefix()` — 静态资源域名
2. `store.loadArea()` — 加载病区
3. `remote` → `startRemoteServices()`；`mock` → `startSimulation()`

## 5. 核心数据流

### 5.1 启动加载

```
loadArea()
  → fetchDoorDeviceList()        # mock 或 remote
  → mapDoorListToTwinArea()      # DoorDeviceInfo[] → TwinAreaEntity
  → enrichAreaBedTemplateIds()   # 每床 queryBedDeviceInfo → templateId
  → area 写入 store
  → AreaScene.updateArea + syncDoorTemplates
```

### 5.2 输液推送（mock）

```
status-channel tick (3.5s)
  → status-pusher → updateBedStatus(bedCode, statusBarInfo)
  → pushHistory (category: infusion)
  → WardScene.updateBedVisual / AreaScene.updateRoomVisual
```

### 5.3 用户选床

```
Raycaster / PlanRenderer click
  → emit bedClick
  → store.selectBed(bed)
  → WardInfoPanel 展示 selectedBed + selectedStatus
```

### 5.4 环境更新

```
env-simulator (mock 5s) / env-fetcher (remote 30s)
  → updateEnv(roomIndex, doorEnvData)
  → analyzeEnvAlert → EnvAlertBanner + WardScene tint + roomSummaries
```

## 6. 类型与领域模型

### 6.1 两层模型

| 层 | 文件 | 说明 |
|----|------|------|
| API 层 | `types/ward.ts` | `DoorDeviceInfo`、`StatusBarInfo`、`DoorSickInfo` |
| 孪生层 | `types/twin.ts` | `TwinAreaEntity` → `TwinWardEntity` → `TwinBedEntity` |

**不要直接在 UI 里用 `DoorDeviceInfo`**，统一走 store 的 `Twin*` 类型。

### 6.2 关键映射

**文件：** `types/twin.ts`

- `mapDoorDeviceToTwinWard(doorData)` — 单门口机 → 单病房
- `mapDoorListToTwinArea(devices)` — 多门口机 → 病区
- `getWardRoomSize(bedCount)` — 1～6 人间房间尺寸
- `BED_LAYOUTS` — 床位在 3D 房间内的 x/z 坐标

### 6.3 输液状态码

**文件：** `types/ward.ts` → `StatusCode`

| 码 | 含义 |
|----|------|
| `300`/`301` | 输液中 |
| `302`/`305` | 输液完毕 |
| `304`/`307` | 离线 |
| `9` | 低电量 |
| `''` | 在院（无输液状态） |

可视化映射在 `core/bed-status.ts` 的 `STATUS_MAP`。

### 6.4 场景与相机

```typescript
type TwinSceneType = 'nurse-station' | 'ward' | 'ward-interior';
type WardInteriorView = '3d' | 'plan';
type CameraPresetId = 'free' | 'door' | 'nurse' | 'top';
```

## 7. 状态中心 twin-store

**文件：** `src/stores/twin-store.ts`

### 7.1 主要 State

| 字段 | 含义 |
|------|------|
| `area` | 整个病区 |
| `currentRoomIndex` | 当前病房索引 |
| `selectedBedCode` | 选中床 |
| `sceneType` | 三场景：`nurse-station` / `ward` / `ward-interior` |
| `wardInteriorView` | 病房内子视图：`3d` / `plan` |
| `cameraPreset` | 3D 相机预设 |
| `statusHistory` | 最近 30 条事件 |
| `dataSource` | `mock` / `remote` |
| `dataWarnings` | SN/设备类型告警 |

### 7.2 主要 Computed

| 名称 | 说明 |
|------|------|
| `currentWard` | 当前病房 |
| `selectedBed` / `selectedStatus` | 选中床及状态元数据 |
| `currentEnvAlert` | 当前房环境告警 |
| `roomSummaries` | 各房汇总（优先级、颜色） |

### 7.3 主要 Actions

| 方法 | 何时调用 |
|------|----------|
| `loadArea()` | 启动、重试、reset |
| `setSceneType(type)` | 切换护士站 / 病房 / 病房内 |
| `enterRoom(i)` | 进入单房（`ward-interior` + cameraPreset=door） |
| `focusRoom(i)` | 走廊模式定位到某房门口 |
| `updateBedStatus()` | 输液推送 |
| `setBedCalling()` | 呼叫推送 |
| `updateEnv()` | 环境更新 |
| `startSimulation()` / `toggleSimulation()` | mock 模拟 |
| `startRemoteServices()` | remote 环境轮询 |

### 7.4 修改 store 时注意

- 改床位数据应改 `area.value.rooms[*].beds[*]` 上的字段，保持响应式
- 新事件类型需扩展 `HistoryCategory` 并在 `pushHistory` 调用处传入

## 8. API 与数据源

### 8.1 数据源切换

**文件：** `api/door-device.ts` → `getDataSource()`

由 `VITE_DATA_SOURCE` 控制：`mock` | `remote` | `database`（默认 mock）。

### 8.4 数据库模式（database）

`database` 模式不让浏览器直连 MySQL，而是通过 `server/db-adapter.mjs` 提供只读后端适配层：

```text
dnk_swp_db
  → server/db-adapter.mjs
  → /db-adapter/api/areas/:areaCode/twin
  → src/api/database-twin.ts
  → twin-store
  → 3D 场景 / 右侧面板
```

启动：

```bash
DB_PASSWORD='你的数据库密码' npm run dev:db-adapter
npm run dev
```

前端配置：

```bash
VITE_DATA_SOURCE=database
VITE_DB_ADAPTER_BASE=/db-adapter
VITE_DB_ADAPTER_TARGET=http://127.0.0.1:8788
VITE_DB_AREA_CODE=2001
```

后端适配器接口：

| 接口 | 说明 |
|---|---|
| `GET /health` | MySQL 连通性检查 |
| `GET /api/areas` | 可用病区列表 |
| `GET /api/areas/:areaCode/twin` | 返回前端统一 `TwinAreaEntity` 及设备、事件、医院信息 |
| `GET /api/templates/:id` | 从 `swp_template_info` 读取模板 |
| `GET /api/hospital` | 从 `hosp_hospital_info` 读取医院信息 |

核心表映射：

| 前端模型 | 数据表 |
|---|---|
| 病区 | `hosp_area_info` |
| 病房 | `hosp_sickroom_info` |
| 床位 | `hosp_bed_info` |
| 患者 | `out_sick_info` |
| 设备 | `swp_device_info` + `swp_device_type` |
| 呼叫 | `swp_call_info` |
| 报警 | `swp_alarm_info` |
| 最新体征 | `swp_physical_info` |
| 高危标签 | `out_sick_high_risk` |
| 模板 | `swp_template_info` |

安全约定：

- 数据库密码只放在服务端进程环境变量，不使用 `VITE_` 前缀。
- 患者姓名默认脱敏，由 `DB_MASK_PATIENT_NAME=true` 控制。
- 适配器目前只读，不提供写库接口。

### 8.2 Remote 数据加载流程

```
fetchDoorDeviceList()
  → querySwpDeviceInfo（一次拉全部门口机）
  → device/doorDevice/queryBaseDeviceInfo（按门口机 SN 拉完整病房/患者/床位）
  → normalizeDoorDevice() 归一化为 DoorDeviceInfo
  → mapDoorListToTwinArea() 转为 TwinAreaEntity
  → enrichAreaBedTemplateIds()（按需补床头 templateId）
```

**无需配置 SN。** 可选 `VITE_AREA_ID` / `VITE_DEPT_ID` 筛选病区。

### 8.3 主要接口（remote）

| Path | 用途 |
|------|------|
| `/swp/swpDeviceInfo/querySwpDeviceInfo` | 门口机 SN 发现 |
| `device/doorDevice/queryBaseDeviceInfo` | **门口机详情（病房、患者、床位主入口）** |
| `iot/.../queryRecentEnvRecordById` | 环境温湿度 |
| `device/bedDevice/queryBaseDeviceInfo` | 床头 templateId（进单房后按需） |
| `/swp/swpTemplateInfo/querySwpTemplateInfoById` | 模板 JSON |
| `device/commonDevice/querySysParamKeyValueByParamKeys` | 文件 CDN 前缀 |

### 8.4 归一化

**文件：** `api/normalize-door.ts`

- 过滤无效床位、按 `bedSort` 排序
- 默认 `deviceTypeCode = '201'`（门口机）
- `mapEnvRecords` 拼接单位（℃、%、dB）

## 9. 服务层（推送与环境）

### 9.1 Pub/Sub 结构

```
status-channel.ts  ──subscribe──► status-pusher.ts ──► store
call-channel.ts    ──subscribe──► call-pusher.ts   ──► store
```

**接真实 WebSocket 时只改 channel 层**，pusher 与 store 可保持不变。

### 9.2 Mock 场景

| 文件 | 周期 | 内容 |
|------|------|------|
| `status-channel.ts` | 3.5s | 901～904 各床输液状态轮换 |
| `call-channel.ts` | 6s | 90102、90308 等呼叫/解除 |
| `env-simulator.ts` | 5s | 温湿度随机波动 |

### 9.3 Remote 环境与刷新

**文件：** `services/env-fetcher.ts` — 启动立即拉一次，之后每 30s 轮询环境。

**文件：** `services/remote-area-fetcher.ts` — remote 模式下每 60s 重新拉取门口机详情，刷新病房、患者、床位与状态基础数据；刷新时保留当前场景位置，不自动跳回护士站。

## 10. 3D / 2D 渲染引擎

### 10.1 WardScene（单病房）

**文件：** `core/ward-scene.ts`（~1500 行）

| 职责 | 关键方法 |
|------|----------|
| 房间壳 | `rebuildRoomShell()` — 尺寸随床位数变 |
| 床位 | `createBedMesh()` / `updateBedVisual()` |
| 床头屏 | `refreshBedTerminal()` → 模板纹理 |
| 相机 | `setCameraPreset()` + lerp |
| 环境 tint | `setEnvAlertLevel()` |
| 点击 | Raycaster → `onBedClick` |

**Vue 包装：** `components/WardScene3D.vue`

```typescript
onMounted: new WardScene → updateWard → syncWardBedTemplates → setCameraPreset
watch ward (deep): updateWard + syncWardBedTemplates
watch cameraPreset / envAlertLevel
onUnmounted: dispose()
```

### 10.2 AreaScene（护士站 + 走廊）

**文件：** `core/area-scene.ts`（~2000 行）

| 阶段 | 说明 |
|------|------|
| `station` | 护士站工作台视角，L 型柜台 + 排班看板 + 天花板灯 |
| `corridor` | 走廊全景，左右交替排房 |

| 职责 | 说明 |
|------|------|
| 走廊布局 | `getRoomLayoutMetrics` 自适应行距 |
| 外立面 | 仅走廊侧薄立面 |
| 门口机 | `buildDoorTerminal` + 横竖屏 |
| 标签 | CSS2D 病房卡片，距离渐隐 |
| 相机 | 工作台 Orbit 约束 / 走廊总览 / `focusRoom` 飞向门口 |

**病房位置公式：**

```
row = floor(index / 2)
side = index % 2 === 0 ? 左(-1) : 右(+1)
z = firstRowZ - row * rowGap
```

### 10.3 PlanRenderer（2.5D）

**文件：** `core/plan-renderer.ts`

- Canvas 俯视图，2/3 列网格
- `ResizeObserver` + DPR
- 点击矩形 hit-test

**Vue 包装：** `components/WardPlanView.vue`

### 10.4 程序化资产

**文件：** `core/hospital-scene-details.ts`（~1600 行）

## 11. 模板渲染子系统

将主项目 SWP 模板 JSON 画到 Canvas，再贴到 Three.js Mesh。

### 11.1 流水线

```
queryTemplateById(id)
  → parseTemplateContent (parser.ts)
  → buildBedTemplateData / buildDoorTemplateData
  → renderTemplateToCanvas / renderDoorTemplateToCanvas
  → THREE.CanvasTexture
```

缓存：`core/template/template-cache.ts`（按 templateId）。

### 11.2 床头 vs 门口

| | 床头 | 门口 |
|--|------|------|
| 渲染器 | `canvas-renderer.ts` | `door-canvas-renderer.ts` |
| 数据 | `data-mapper.ts` | `door-data-mapper.ts` |
| 纹理出口 | `bed-terminal-texture.ts` | `door-terminal-texture.ts` |
| 结构 | 扁平 nodes | 含 `doorInfoBox` 多床嵌套 |

### 11.3 parser 要点

**文件：** `core/template/parser.ts`

- 跳过 button、倒计时 cover 等节点
- 像素坐标 → 百分比（`analyzeType !== '2'`）
- `doorInfoBox` 注入空床模板（`door-empty-bed.ts`）
- 按 `zIndex` 排序

| id | 数据 |
|----|------|

| `bedNum` | 床号 |
| `patientName` | 患者名 |
| `nursingLevel` | 护理等级 |

### 11.5 门口机节点 ID 速查

| id | 数据 |

### 11.6 横竖屏

**文件：** `core/template/door-screen-orientation.ts`

- `director '0'` = 横屏，`'1'` = 竖屏

#### 本月优化

- 优化 SWP 活动事件查询和轮询，只有接口返回 `eventStatus=0` 的记录才作为当前活动事件处理。
- 移除基于时间的“疑似历史未结束”判断，避免前端自行隐藏真实的活动呼叫；SWP 呼叫在平台内保持“呼叫中”，页面只提供定位。
- 增加定位字段诊断：区分“定位字段缺失”和“设备或床位编码未匹配”，方便排查后端上报字段和编码映射问题。
- 在任务卡中记录实际定位来源；标准接口字段显示“接口字段定位”，只有 `callFrom` 完全匹配已有房间、床位或设备编码时才显示“呼叫源编码定位”。
- 移除数字孪生页面对 `/device/commonDevice/saveCallEvent` 的调用，避免没有语音通道的浏览器页面伪造已接听状态；后端 `eventStatus=0` 仍是活动呼叫的唯一依据。
- 呼叫卡明确提示“请在护士站管理机或话机上接听”；真正接听仍由管理机或话机完成。
- 移除活动 SWP 呼叫的“本地隐藏”和恢复入口，避免后端仍在呼叫时被浏览器本地状态遮蔽；旧的本地隐藏记录也不再影响活动呼叫。
- 增加可手动开启的呼叫提示音和浏览器系统通知，同一呼叫批次只提醒一次，避免每轮查询重复响铃。
- 页面处于后台时，活动呼叫查询由前台每 15 秒调整为后台每 60 秒，回到前台后立即补刷，兼顾提醒时效和接口压力。
- 修复活动呼叫查询复用历史统计分页导致的连续请求：`querySwpCallInfo` 和活动报警每轮只读取一页，近24小时响应统计继续分页且最多读取 20 页。
- 优化护士站任务操作区：默认展示 4 条优先任务，超出后支持展开全部和收起；SWP 呼叫只保留定位，环境、设备、输液等任务继续支持标记“处理中”和完成处理。
- 呼叫提醒开关通过浏览器 `storage` 事件同步到同源的其他标签页；旧的 SWP “已查看/本地隐藏”记录不再影响活动呼叫展示。
- 增加呼叫源编码的保守定位兼容：标准定位字段为空时，仅在 `callFrom` 与现有房间、床位或设备编码完全一致时定位，不解析病房床位描述文本。
- 优化护士站任务排序：先按告警级别，再按发生时间从早到晚排列，让等待时间更长的同级呼叫优先展示。
- 增加任务等待时长展示，护士站任务卡会按当前时间显示已等待的分钟、小时或天数，并每 30 秒更新一次。
- 收紧活动呼叫生命周期：只要 SWP 接口仍返回活动事件，呼叫卡就持续显示；只有后端不再返回该活动事件时才从页面消失。
- 优化护士站呼叫列表视觉：活动呼叫增加信号脉冲、低频扫描光、实时状态指示和定位按钮光效，使任务卡与数字孪生 3D 场景风格统一；系统开启“减少动态效果”时会自动停用动画。
- 进一步精简呼叫卡：只保留护士能直接使用的级别、患者呼叫内容、接听提示、发生时间和当前状态；隐藏接收终端、接口返回、定位诊断、位置来源等技术字段，避免信息堆叠。
- 按“来源 ID + 发生时间”区分同一设备的不同呼叫批次；同一批次仍去重，不同发生时间会生成独立任务。
- 优化护士站任务优先级：同级任务中新的待处理呼叫优先于已进入“处理中”的旧呼叫；超过 5 分钟进入关注色，超过 10 分钟进入紧急色。
- 统一护士站呼叫 KPI 与告警任务列表的数据口径，避免 KPI 数量和实际展示列表不一致。
- 顶部增加数据源和健康状态提示，区分实时 SWP、数据库、模拟数据，以及同步中、部分同步、同步失败和数据过期状态。
- 优化告警到 3D 场景的联动：从任务卡进入床位后自动聚焦并高亮 8 秒，手动选床、离开场景或处理完成后自动清除高亮；无定位事件只停留在护士站。
- 优化 SWP 事件轮询：页面隐藏时暂停事件和响应指标请求，页面恢复可见时只补刷一次，并继续保留请求防重入和病区切换保护。
- 优化 SWP 事件异常轮询：接口连续失败时采用 30 秒、60 秒的短暂退避，避免服务异常期间持续高频请求；接口恢复后自动回到正常轮询频率。
- 优化护士站呼叫数据状态提示：正常时显示“呼叫数据已同步”；部分异常时提醒数据可能延迟并关注管理机或话机；完全异常时保留最近一次呼叫数据并明确标注，不向护士直接展示接口报错。
- 完善设备异常闭环：区分设备离线、异常离线和低电量，任务卡分别提示检查电源网络、检查设备连接或充电更换电池；设备恢复正常后告警自动消失。
- 统一设备异常口径：护士站汇总和病区房间状态分别统计离线、低电量，避免把低电量设备误显示为普通离线。
- 完善病房环境异常闭环：按温度、湿度、空气质量和噪音生成护士可执行的复核提示，多项异常统一汇总；环境恢复正常后任务自动消失。
- 统一环境读数展示：温度、湿度和噪音分别规范为 `℃`、`%`、`dB`，空气质量为“差”时按严重异常处理，避免漏报。
- 完善输液巡视闭环：`300/301` 统一显示“输液中”并生成“输液巡视”任务，提示护士按计划确认滴速和通路；`302/305` 显示“输液已完成”但不自动生成待处理任务，避免把已结束状态误当成新告警。
- 区分日常巡视和紧急响应：护士站新增“输液巡视”床位数，响应压力统计不再把普通输液巡视计入紧急告警数量，避免护士误判当前工作压力。
- 补充病区巡视闭环：重点病房列表同时显示待处理任务或待巡视床位数，点击病房即可进入对应场景，状态以最新真实数据自动刷新。
- 增加护士交班摘要：自动汇总本班未结束呼叫、设备异常、环境异常病房、输液待巡视和实时数据同步状态；只使用当前真实数据，不虚构处理人和处理时间。
- 收紧告警处理闭环：设备、环境和输液活动任务只允许标记“处理中”，不能由浏览器手动完成或隐藏；真实来源恢复后任务自动结束，并清理本次处理状态，下一次新异常重新进入待处理。
- 增加数据健康闭环：护士站分别展示床位患者、设备、环境、输液、呼叫报警的数据状态；病区四类数据沿用同一次病区快照口径，不虚构独立刷新时间，任何数据延迟或中断时都禁止页面据此判断“病区无异常”。
- 优化远程数据刷新、加载状态、错误提示、场景切换和相机过渡，尽量保留用户当前查看的病区和视角。
